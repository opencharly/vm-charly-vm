# 2026.271.0654 — docs(skill): make the VM disposability + deploy cross-ref unambiguous

## Summary

Clarify the `/charly-vm:vm` skill's **disposability + deploy cross-ref** so the entity-vs-deploy rule is unambiguous and non-contradictory.

The skill already said *"disposability is a deployment property, never a VM-entity field"* — but it did **not** say what automation must DO when it creates + destroys a VM autonomously, which left a bed free to infer authorization from its own name/`lifecycle:` tag and destroy a shared entity. This adds the missing rule:

- **An ephemeral VM that automation creates + destroys MUST be named by a `disposable: true` `vm:` DEPLOY — never the entity.** With the worked pattern: declare a per-run `<name>: { vm: { from: <entity>, disposable: true } }` and key EVERY verb to it with `--domain <deploy>` (`vm create` / `vm stop` / `vm snapshot create` / `vm destroy`, and `vm bake --domain <deploy>`).
- **`vm bake --domain <deploy>`** also sets the create's non-destructive `--keep-disk`, **because a golden captured on the domain backs onto the domain's disk** — recreating that disk drops the golden's backing and the bake would boot an empty overlay.
- **A bed that destroys a shared entity (or a domain not handed to it as `disposable: true`) is a B17 violation** — authorization derives from the destroyed TARGET, never the bed's name or `lifecycle:` tag.

This is the wording that makes `check-cua-fleet-build-local` (distro-omarchy#62) the *obvious* shape rather than a discovery: two `disposable: true` deploys (`cua-container-disk-produce`, `cua-produced-consume`) driven via `--domain`.
