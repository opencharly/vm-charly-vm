# 2026.242.2205 — docs(vm): the omarchy VM skill, and four source kinds instead of two

## Summary

`omarchy-vm`, `omarchy-pacstrap-vm` and the `charly-omarchy` keeper have shipped and are
gated by three `disposable: true` beds, and **no skill mentioned any of them**. A reader
following this family had no way to learn that `source.kind: iso` exists, let alone how its
seed works.

Two changes: a new `omarchy-vm-skill`, and a correction to `vms-catalog`, which described
`kind: vm` as sourced two ways when it has been four for some time.



Covers all three entities and which bed proves what, plus the decisions that are easy to get
wrong and expensive to rediscover:

- **why the ISO VM is deliberately unencrypted** — an encrypted install is not actually
  unattended (someone types the LUKS passphrase at first boot) and its passphrase would sit
  in PLAINTEXT in the seed's `disk_encryption` block;
- **the disk-first boot order**, which removes a whole subsystem: the firmware falls through
  the blank disk to the ISO on the first boot and boots from disk ever after, so there is no
  eject, no detach, and the reboot-loop failure mode cannot occur;
- **why the pacstrap builder is based on `omarchy` and not `arch.arch`** — pacstrap resolves
  against the BUILDER's `/etc/pacman.conf`, and charly appends `extra_repo` without
  rewriting `[core]`/`[extra]`, so a plain-Arch builder silently produces a MIXED snapshot
  that pacman reports success for;
- **that `charly-omarchy` is a DEPLOY of the template, not a third template**, and that the
  beds derive from the template rather than from the keeper;
- four gotchas measured the hard way: a bootstrap VM is not the distro unless the
  metapackage is in `source.package`; the ESP is at `/boot` with a UKI and
  `root=PARTUUID=`; the bootstrap path registers no named NVRAM entry so `/proc/cmdline` is
  the right assertion; and these builds need ~22 GiB on the staging dir, which `/tmp` often
  is not.

`owner: charly-vm`, matching every sibling skill in this repo.

## vms-catalog: four source kinds, not two

The catalog described `kind: vm` as pairing "with either a remote cloud-image URL
(`source.kind: cloud_image`) or an in-repo bootc container image (`source.kind: bootc`)"
and listed only those two. Both `bootstrap` and `iso` have shipped since. A reader
consulting the authoring reference to find out what a VM can be sourced from was told half
the answer, and `iso` — the newest and least obvious — was invisible.

Added both to the list, with the `iso` entry carrying the one structural fact that makes it
comprehensible: the answer FORMAT belongs to the distro (`#DistroInstaller`) and the answer
DATA belongs to the VM entity (`installer:`).

Also corrected `#DistroID (13 ids)` → `(14 ids, omarchy included)`; the vocabulary is
`almalinux alpine arch archarm cachyos centos debian endeavouros fedora manjaro omarchy rhel
rocky ubuntu`.
